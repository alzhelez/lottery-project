# Архитектура

```
браузер ──► Next.js (src/)  ──spawn──►  python/lp.py  ──►  python/lottery/*
               │  API-маршруты              │ события @@{json} в stdout
               │  менеджер задач            ▼
               └──── читает ────────►  data/draws/*.txt, data/results/*.json
```

## Python-движок (`python/lottery/`)

| Модуль | Назначение |
|--------|------------|
| `games.py` | Реестр игр (`config/games.json`), пути к данным |
| `drawfile.py` | Разбор и запись файлов тиражей, слияние legacy-файлов, определение формата игры по данным (поля «k из N», позиционные блоки для цифровых игр), матрицы индикаторов |
| `stoloto.py` | Клиент API Столото и инкрементальная загрузка: архив читается окнами дат по страницам; окно, которое API не может пролистать до конца (после ~500-й страницы он повторяет одну и ту же), уменьшается под частоту тиражей игры |
| `stats.py` | Тесты случайности, поправки Холма и Бенджамини–Хохберга, описательная статистика |
| `models.py` | Модели прогноза. Каждая строит матрицу оценок `S[t]` только по тиражам `< t` |
| `evaluate.py` | Бэктест с разделением «отбор / контроль», консенсус методов |
| `godmode.py` | Онлайн-адаптация: эксперты + мета-стратегии (лидер за W тиражей, Hedge) |
| `journal.py` | Журнал прогнозов: запись до тиража, сверка после загрузки, итоги |
| `odds.py` | Калькулятор шансов: вероятности исходов, ожидаемый возврат; призы — свои или типичные из архива |
| `prizes.py` | Разбор категорий выплат из ответа API, хранение (`data/draws/prizes_<игра>.jsonl`), типичные выплаты |
| `money.py` | Оценка методов в рублях: выплаты за прогнозы против случайного выбора на тех же тиражах |
| `popularity.py` | Популярность чисел у игроков по числу победителей (гребневая регрессия + перестановочный тест) |
| `scan.py` | Проверка всех игр на случайность: кэш по подписи архива, параллельный пересчёт |
| `notify.py` | Уведомления в Telegram (Bot API): настройка из `.env`, сообщения о журнале, автозапуске, режиме Бога, ошибках |
| `tickets.py` | Признаки популярных комбинаций, генератор (с учётом модели популярности, если она значима) и проверка комбинаций |
| `export.py` | Экспорт в Excel и CSV |
| `rules.py` | Правила игр со stoloto.ru: «Как проходят розыгрыши» (CMS), таблица выигрышей тиража, суперприз; разбор расписания (время → лототрон/ГСЧ), официальные выигрыши по категориям. Хранение — `data/rules/<игра>.json` |
| `mechanics.py` | Способ розыгрыша каждого тиража (API → расписание → эпоха), проверки по способам и их сравнение, порядок выпадения шаров, повторяемость находок по половинам истории, «что исключено» (минимальный обнаружимый эффект), дрейф |
| `chaos.py` | «Порядок из хаоса»: состояние тиража (5 признаков), поиск аналогов (`knn_predict` — только прошлое, окно 4000 состояний), методы аналогов / фазового пространства / порядковых паттернов, проверки предсказуемости, энтропии перестановок и рекуррентности против перемешанных копий; всё — отдельно по способу розыгрыша, прогноз — из набора способа ближайшего тиража |
| `repeats.py` | Гипотезы о повторах по позициям: автокорреляция индикаторов «тираж × число» по позициям и «тираж × позиция» по числам через двумерное БПФ — совпадения для всех задержек и сдвигов сразу; точный хвост Пуассона, Бонферрони, повторяемость по половинам |
| `order.py` | Порядок выпадения: счётчики «число × позиция» по тиражам того же способа, сэмплирование Дирихле и расстановка венгерским алгоритмом; проверка угадываемости порядка на истории |
| `nextdraw.py` | Ожидаемый возврат ближайшего тиража: Σ P·приз + P(суперприз)·суперприз·(1−e^−λ)/λ, λ = продажи·P(суперприз); `results/nextdraw.json`, отбор для уведомления |
| `fsutil.py` | Запись файлов с повторами: на Windows файл может держать антивирус или индексатор |

`python/lp.py` — единая точка входа: `fetch`, `scan`, `analyze`, `godmode`, `journal`, `auto`,
`odds`, `tickets`, `export`, `info`, `diagnose`, `telegram`. Короткие команды (`odds`, `tickets`, `export`) Next.js
вызывает синхронно (`runEngine`), длинные — как фоновые задачи.
В терминале команды печатают текст, при запуске из приложения — события `@@{json}`.
Результаты пишутся атомарно (временный файл + переименование).

### Формат файла тиражей

```
ДД.ММ.ГГГГ ЧЧ:ММ||НОМЕР||a, b, c, d||e, f, g, h
```

Блоки через `||`. Старые 3-частные строки (все числа одним блоком) режутся по подсказке
`counts` из реестра. Формат игры определяется по данным: если в блоке числа не повторяются —
это поле «k из N»; если повторяются (цифры) — каждая позиция становится отдельным блоком
«1 из 10».

Если количество чисел в блоке меняется (бинго), блок становится множеством переменного
размера: «Выпавшие числа», если в среднем выпадает не больше половины диапазона, иначе
«Невыпавшие числа» (дополнение). Если числа записаны в порядке выпадения, добавляется
блок «Первые 10 шаров». Диапазон и названия блоков можно задать в реестре (`range`,
`labels`) — так Русское лото, где API отдаёт только невыпавшие числа, получает диапазон 1–90.
Ожидание случайного выбора считается по каждому тиражу: K прогнозных чисел против k_t
чисел блока из N — гипергеометрическое распределение; все метрики суммируют эти ожидания.

### Сэмплирование Томпсона и целевой тираж

* `Features.sampled(kind, param, seed)`: для частотных методов вместо частоты берётся
  θ ~ N(m, m(1−m)/(n+2)), m = (c + p)/(n + 1) (окно) или сглаженная экспоненциальная
  частота с n_eff = (1+λ)/(1−λ). Случайность — `tie_noise(t, число, seed)`, seed — crc32 ключа
  метода: значение для тиража t не зависит от будущих тиражей и от длины истории.
* `journal.target_draw(data, now)`: ближайший тираж из правил (API), если до него больше 90 с;
  иначе от последнего известного тиража (API или архив) шагами расписания или 10-го процентиля
  интервалов до первого времени позже now + 90 с. Архив старше 3 дней — «последний + 1».
  Номер общий для всех источников одного анализа (`evaluation.target`, `chaos.next.draw_no`).

### Журнал прогнозов

`data/journal/<игра>.json`. `analyze` записывает прогноз лучшего метода и консенсус,
`godmode` — прогноз выбранной стратегии после каждой стадии; повторный прогноз того же
источника на тот же тираж заменяет прежний. После загрузки тиражей `fetch` сверяет
записи: статус `checked`, если прогноз сделан раньше времени тиража, иначе `late` (в итог
не входит). Для устаревших игр прогнозы не записываются.

### Актуальность игр

Игра активна, если последний тираж не старше `inactive_days` (15) дней на момент последней
проверки архива загрузчиком (`data/draws/draws_<игра>.meta.json`, поле `checked_at`);
если архив не проверялся — на текущий момент. Логика одинакова в Python и в Next.js.

### Модели

* частотные: горячие и холодные за окно, экспоненциально взвешенная частота;
* давность: давно не выпадавшие / недавно выпадавшие;
* связи: марковская цепь переходов (с забыванием), пары с числами прошлого тиража;
* смеси частоты и давности;
* обучаемые: онлайн-логистическая регрессия, градиентный бустинг с периодическим
  переобучением, случайные линейные комбинации признаков;
* контроль: случайный выбор.

Ничьи разбиваются детерминированным хешем от (тираж, число) — прогноз на тираж не меняется
при добавлении новых тиражей.

### Режим Бога

1. Пул экспертов растёт стадиями: базовые → расширенная сетка → бустинг → случайный поиск
   комбинаций признаков. После каждой стадии результат сохраняется.
2. Мета-стратегии на каждом тираже выбирают эксперта (лидер за 50…все тиражи) или
   взвешивают их (Hedge с параметрами η и забыванием γ).
3. Стратегия выбирается по первой половине тиражей, её результат показывается по второй.
4. Бюджет времени — до 8 часов; режим заканчивает раньше, когда поиск 40 пачек подряд не
   улучшает лучшего эксперта на первой половине («перебор исчерпан»).
5. Пул ограничен 800 экспертами: слабейшие по первой половине вытесняются (вторая половина
   в отборе не участвует).
6. Состояние (угаданные экспертами числа по тиражам — `uint8`, пройденные стадии, ход поиска,
   состояние генератора) сохраняется в `data/results/<игра>/godmode_state.npz` после стадий
   и раз в 5 минут; `--resume` продолжает с него, если архив тиражей не изменился. Краткая
   сводка — в `godmode_state.json` (её читает интерфейс). Сохранение удаляется, когда
   перебор исчерпан, когда `fetch` добавил тиражи, и если ему больше 14 дней.
   Голосование экспертов в мета-стратегиях векторизовано (`np.bincount` по пачкам тиражей),
   промежуточный пересчёт стратегий во время поиска — не чаще раза в 10 минут.
7. Процесс пишет `godmode.lock` (PID) и `godmode.progress.json`: так интерфейс видит запуск
   из консоли или Планировщика и может его остановить. На Windows проверка PID в Python идёт
   через WinAPI — `os.kill(pid, 0)` там завершает процесс.

### Выплаты и популярность

При загрузке `stoloto.py` передаёт сырой тираж в `prizes.extract`: тот ищет в ответе список
категорий (комбинация, число победителей, сумма) по нескольким вариантам имён полей и
приводит подпись категории к ключам исходов (`4 X 3 и 3 X 4` → `4+3`, `3+4`; `5` в игре с
бонусом → `5+0`; `2 или 10` → `2`, `10`). Файл — JSONL с компактными строками
`{"no", "src", "p": цена, "s": продажи, "c": [[подпись, победители, выплата], …]}`; новые тиражи
дописываются в конец, файл целиком переписывается только при изменении сохранённых.
Тиражи со статусом не `COMPLETED` в выплаты не попадают. Последние два сырых ответа игры
сохраняются в `data/api_samples/<игра>.json` — `diagnose` показывает, какие поля найдены.

* `money.py` — для каждого тиража берётся его собственная таблица выплат: прогноз метода
  оценивается суммой, которую получил бы билет; случайный выбор — точным ожиданием выплаты
  по гипергеометрическому распределению. Нужны ≥30 тиражей с выплатами и цена билета.
* `journal.py` — при сверке к прогнозу дописывается выигрыш `won` по выплатам этого тиража.
* `popularity.py` — `y_t = log(победителей) − скользящая медиана(51)`, `y ≈ X·β`, где `X` —
  индикаторы выпавших чисел; гребневая регрессия, значимость — 200 перестановок `y`.
  Результат — `data/results/<игра>/popularity.json` (пишет `analyze`); `tickets.py`
  оставляет только билеты, которые по суммарной популярности чисел входят в 30% наименее
  популярных случайных билетов.

### Правила, способ розыгрыша, дрейф, ближайший тираж

* `rules.fetch` (из `fetch`/`auto`, не чаще раза в 20 часов на игру): `games/info-new` (ближайший
  тираж), `games/<игра>/winning-table?drawNumber=N` (нужны заголовки gosloto-partner и
  gosloto-token), CMS `about-lottery-categories/<игра>` (тексты how_draws_work, faq,
  about_prize; плейсхолдеры `{{lottery_winners_distribution_pers}}` и
  `{{lottery_jackpot_guaranteed}}` подставляются из данных тиража) и
  `winning-table-superprize/<игра>`.
* Таблица выигрышей — строки `(g1, g2)`: два поля — g1+g2; поле и бонус; одно поле — g2 = 0;
  «12 из 24» — (a, b) значит «a или b»; Кено — g1 = сколько чисел выбрано, g2 = совпадения.
  `official_prizes` переводит их в ключи категорий калькулятора шансов.
* Способ тиража (`mechanics.mechanism_of_draw`): 1) из сырого ответа API при загрузке — есть
  `videoLink` → лототрон, секунды времени ≠ 00 → ГСЧ (`prizes.extract` пишет `m`); 2) время
  тиража по расписанию из текста «Как проходят розыгрыши» (время без пометки — лототрон, если
  лототрон в тексте упомянут); 3) в смешанной игре минуты не 00/30 → ГСЧ, ровный час →
  лототрон; 4) до первого тиража ГСЧ — лототрон; 5) игра с одним способом — он.
* Проверки по способу (≥ 200 тиражей): все тесты случайности, сравнение частот двух способов
  (хи-квадрат), порядок выпадения (хи-квадрат по позиции шара, только лототрон, поправка Холма).
* Повторяемость (`mechanics.replicate`): тест с поправкой p < 0,05 должен дать p < 0,05 и в
  каждой половине истории; для частот — ещё и положительная корреляция отклонений половин.
  Иначе находка снимается с пометкой в `detail`.
* «Что исключено»: δ = (z₁₋α/(2N) + z₀.₈)·√((1−p)/(T·p)) — относительное отклонение частоты
  одного числа, которое тест найдёт с мощностью 80%; для методов — (1,96 + 0,84)·σ/√n/среднее.
* Дрейф: окно W = clip(T/10, 200, 2000) последних тиражей против остальных, частоты и суммы,
  поправка Холма, тревога при p < 0,01; `results/<игра>/drift.json` хранит прошлые тревоги,
  чтобы сообщать о новой один раз.
* Ближайший тираж: продажи — медиана последних 30 тиражей без аномалий; аномалия — продажи
  меньше 10% от медианы соседних ±50 тиражей.

### Порядок из хаоса

* Состояние перед тиражом u — признаки тиражей u−1…u−E (`embed`); для строки t ищутся
  ближайшие состояния u < t и усредняется то, что выпало в тираже u. Аналоги — близость =
  число общих чисел (скалярное произведение индикаторов), веса e^(близость − max); фазовое
  пространство — евклидово расстояние с масштабом признаков по тиражам < t, веса симплекса
  e^(−d/d_min). Порядковые паттерны — номер перестановки окна из d средних чисел.
* Проверки: предсказуемость — корреляция симплекс-прогноза среднего числа с фактом (t-тест,
  Бонферрони по E = 1…5); энтропия перестановок (d = 4) против 199 перемешанных копий;
  DET рекуррентного анализа (E = 3, 1000 состояний, порог — 10% ближайших пар) против 99
  перемешанных копий. Холм по всем проверкам набора; находка засчитывается, если p < 0,05 в
  обеих половинах истории.
* Наборы — `mechanics.split_by_mechanism` (или все тиражи, если способ не определён);
  методы — `evaluate_game(sub, models=chaos_models())` на последних 20 000 тиражах набора.
* Способ ближайшего тиража (`next_mechanism`): номер и время ближайшего тиража из правил
  (секунды → ГСЧ, иначе расписание) → следующее время расписания после последнего тиража.
  Прогноз лучшего на отборе метода этого набора — в журнал (`source = chaos`).

### Автозапуск

`lp.py auto` — один цикл: `fetch` всех игр (с автоматической сверкой журнала) → `analyze`
каждой активной игры, архив которой изменился (прогноз в журнал) → при `--godmode-budget N`
режим Бога → `scan` (пересчитываются только изменившиеся игры) → сводка в Telegram.
Статус — `data/auto_status.json`, журнал — `data/logs/auto.log`, блокировка — `data/auto.lock`.
`--every N` повторяет цикл каждые N часов (так работает контейнер `auto` в Docker).

## Next.js (`src/`)

| Путь | Назначение |
|------|------------|
| `app/page.tsx` | Список игр, модальное окно загрузки, проверка на случайность |
| `app/games/[slug]/page.tsx` | Страница игры: ссылка на stoloto.ru, число тиражей, период, следующий тираж; вкладки «Обзор», «Сравнение методов», «Режим Бога» |
| `app/api/games` | Список игр со сводкой и вердиктами |
| `app/api/games/[slug]` | Сводка по игре |
| `app/api/games/[slug]/results` | Сохранённый анализ или результат режима Бога |
| `app/api/games/[slug]/journal` | Журнал прогнозов игры и итоги по источникам |
| `app/api/games/[slug]/odds` | Шансы игры; PUT — сохранить цену и призы |
| `app/api/games/[slug]/tickets` | Генерация билетов и проверка комбинации |
| `app/api/games/[slug]/export` | Файл Excel или CSV |
| `app/api/odds` | Шансы всех игр (страница «Шансы игр») |
| `app/api/auto` | Статус автозапуска |
| `app/api/telegram` | Состояние уведомлений; POST — тестовое сообщение |
| `app/api/jobs`, `app/api/jobs/[id]` | Запуск, статус, остановка фоновых задач |
| `lib/jobs.ts` | Менеджер задач: запускает Python, разбирает события, не даёт запустить две одинаковые задачи; после загрузки сам запускает проверку на случайность |

Задачи живут в памяти сервера, результаты — на диске. После перезапуска сервера идущая
задача теряется, но сохранённые результаты (включая промежуточные результаты режима Бога)
остаются.

## Тесты

* `tests/pytest` — 208 тестов движка: разбор файлов, форматы API и выплат, загрузка на поддельном API,
  калибровка тестов случайности, отсутствие утечки будущего в каждой модели и мета-стратегии,
  популярность, Telegram (на поддельном Bot API), производительность, CLI.
* `tests/e2e` — Playwright: полный путь пользователя на моке API Столото
  (`tests/mock_stoloto/server.py`). Мок сдвигает даты активных игр к вчерашнему дню, отдаёт
  «закрытую» игру со старыми датами, бинго в обоих форматах API и придерживает последний
  тираж 4x20 до запроса `/__release` — так проверяется сверка журнала.
* Allure: pytest-маркеры `allure_label` (epic/feature) ставит `conftest.py`, сквозные тесты
  размечаются через `allure-js-commons`; отчёт собирает Allure 3 (`allurerc.mjs`).
* `tests/api` — API-автотесты (14 сценариев) на Python (pytest + requests), Go (`testing`)
  и Java (TestNG + REST Assured + AssertJ); окружение — `tests/api/env.py` (мок + приложение
  на :3100 с отдельной папкой данных). Go-результаты переводит в JUnit XML
  `tests/api/go/cmd/gojunit`. Подробно — `tests/api/README.md`.
* CI: `.github/workflows/ci.yml`.
